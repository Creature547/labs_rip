# Лабораторная 4 — отопительные приборы

Проект сделан на основе переданного рабочего архива ЛР3. Стек: Go, Gin, GORM,
PostgreSQL, MinIO; добавлены JWT, Redis и Swagger UI. Работа регистрации сохранена:
пароли в PostgreSQL хранятся как bcrypt-хеши. Все зарегистрированные пользователи
работают в группе «создатель». Гость — запрос без действительного JWT.

## Первый запуск

Работайте из папки awesomeProject, где находится go.mod. Существующие PostgreSQL
и MinIO оставьте запущенными. Запустите только новый сервис Redis:

```bash
docker compose up -d redis
go mod tidy
go fmt ./...
go test ./...
go run ./cmd/awesomeProject
```

`go mod tidy` обязателен при первом запуске: он загрузит новые библиотеки и
дополнит go.sum. Версия Go и существующие зависимости взяты из вашего архива.
Swagger: http://localhost:8080/swagger/index.html

Для запуска вместе с проверкой есть `bash start-lab4.sh` или
`powershell -File start-lab4.ps1`. Они не запускают контейнеры.

Если это полностью новое окружение, сначала:

```bash
docker compose up -d
go mod tidy
go run ./cmd/migrate
```

Для вашей уже рабочей БД миграция повторно не требуется: структура таблиц ЛР4
не менялась. Не удаляйте Docker volumes. Миграция из ЛР3 оставлена в проекте.
Параметры PostgreSQL/MinIO сохранены, к .env добавлены REDIS_ADDR, REDIS_PASSWORD
и случайный JWT_SECRET. Секрет не публикуйте в Git; .env.example содержит шаблон.

## Аутентификация в Swagger

1. Откройте Swagger в инкогнито.
2. Выполните `POST /api/users` с новым логином и паролем:
   `{"login":"anna_lab4","password":"lab4pass"}`. Ожидается 201.
   Если такой логин уже зарегистрирован, будет 409 — используйте существующий
   пароль или новый логин.
3. Выполните `POST /api/users/auth` с теми же данными. Ответ 200 содержит
   `access_token`, `token_type`, `expires_in` и `user`.
4. Нажмите **Authorize**. Введите **Bearer**, пробел и значение access_token:
   `Bearer eyJ...`. Сохраните авторизацию.
5. Выполните `GET /api/heating-equipment`. Для фильтра можно задать
   `min_power=1`, `max_cost=10000` или часть названия в `name`.

Для Go используются JWT, а не cookie-сессии. В Application искать куки не нужно.
Авторизация действует на защищённые методы Swagger; список и лента доступны
без Authorize. Swagger UI обслуживается локально через gin-swagger и swaggo/files.

## Postman

Импортируйте `postman/Lab4.postman_collection.json`. Файлы
`sample-image.png` и `sample-video.mp4` находятся рядом. В запросе создания
черновика выберите их через Select Files, если Postman не нашёл относительные пути.

Коллекция содержит переменные base_url, login, password, token, equipment_id.
Для токена, полученного в Swagger, вручную заполните переменную **token** в
коллекции. В защищённых запросах уже задан Bearer Token `{{token}}`.
При входе через Postman token сохраняется автоматически; при создании черновика
автоматически сохраняется equipment_id. Вкладка Tests содержит проверки статусов.

Порядок работы: регистрация → вход → создание черновика → получение черновика →
публикация → список/лента → лайк → выход. Удаление — отдельная операция;
не выполняйте её до скриншотов публикации и ленты. Создание требует name, power,
cost, image и video; description необязательно. power и cost должны быть > 0.
PUT публикации выполняется без тела, данные уже записаны в черновик, как в ЛР3.

Для чужого черновика публикация/удаление возвращают 404: доступ ограничен
creator_id из JWT. Идентификатор создателя из запроса не принимается.
В базе меняются status и formed_at, в ответ публикации добавлены именно эти поля.

## Скриншоты для сдачи

| № | Что выполнить | Что должно быть видно |
|---|---|---|
| 1 | POST /api/users/auth в Swagger в инкогнито | Данные входа, статус 200, JWT в ответе |
| 2 | GET /api/heating-equipment в Swagger | Статус 200 и опубликованные приборы |
| 3 | Перенести JWT в Postman, GET своего черновика после его создания | Bearer Token, ответ 200, успешная проверка Tests |
| 4 | GET списка в Postman с Authorization → No Auth | 200 и список |
| 5 | GET списка с Bearer invalid-token | 200 и список; есть готовый запрос в папке проверок |
| 6 | PUT публикации существующего черновика гостем | Authorization → No Auth, 401 |
| 7 | PUT того же черновика с действительным JWT | 200, status=опубликован и formed_at |
| 8 | После успешной публикации выполнить Logout и показать Redis | blacklist:<jti>, login и TTL |
| 9 | Открыть sequence в StarUML | У сообщения поле signature ссылается на операцию доменного класса |

Redis при JWT не хранит активные сессии. До Logout blacklist может быть пуст:
это нормально. Для скриншота 8 сначала выполните POST /api/users/logout с тем же
токеном, затем откройте CMD/терминал:

```bash
docker exec -it heating_redis redis-cli
SCAN 0 MATCH blacklist:* COUNT 100
```

Скопируйте найденный ключ и выполните (вместо <jti> подставьте значение):

```text
GET blacklist:<jti>
TTL blacklist:<jti>
```

GET покажет логин пользователя. TTL — оставшееся время в секундах. При TTL=-2
ключ уже истёк: войдите ещё раз и выполните Logout новым токеном. У JWT срок
действия 3600 секунд. После Logout старый токен даёт 401 на защищённых запросах;
для дальнейшей работы выполните вход заново. Logout не блокирует другие JWT
того же пользователя.

При недоступном Redis защищённые запросы возвращают 503. Общедоступное чтение
продолжает работать, а пользователь в ответе считается гостем. При старте сервер
проверяет подключение к Redis и не запускается, если оно не удалось.

## Методы

| Метод | Путь | Доступ |
|---|---|---|
| POST | /api/users | Все — регистрация |
| POST | /api/users/auth | Все — вход |
| POST | /api/users/logout | Создатель |
| GET | /api/heating-equipment | Все, фильтры name/min_power/max_cost |
| POST | /api/heating-equipment | Создатель |
| GET | /api/heating-equipment/draft | Создатель, только свой черновик |
| PUT | /api/heating-equipment/:id/publish | Создатель, только свой черновик |
| DELETE | /api/heating-equipment/:id | Создатель, только свой прибор |
| POST | /api/heating-equipment/:id/like | Создатель |
| GET | /api/heating-equipment/feed | Все |
| GET | /api/heating-equipment/feed/:id?next=true | Все |

В переданном актуальном архиве было 11 HTTP маршрутов: лента имеет два варианта
адреса (без ID и по ID). Они сохранены. Дополнительные сценарии Postman не
добавляют серверных маршрутов. Адрес /swagger — интерфейс документации.

## Обновление Swagger

Готовый swagger.json уже включён и регистрируется в docs/docs.go.
Все обработчики снабжены swag-комментариями. Для генерации из комментариев:

```bash
go run github.com/swaggo/swag/cmd/swag@v1.16.4 init -g cmd/awesomeProject/main.go
```

После изменения методов обновите документацию. Требование JWT указано только
у защищённых операций; регистрация и вход по смыслу доступны без JWT.

## Проверка этой версии

Проверены структура ZIP, JSON Swagger/Postman, соответствие маршрутов описанию,
настройки Redis, ссылки и отсутствие фиксированного пользователя в обработчиках.
Добавлены тесты: проверка подписи и срока JWT, запрет другого алгоритма,
блокировка при Logout и изоляция других токенов, доступ гостя, недоступный Redis,
разделение пользователей между запросами. В среде подготовки отсутствуют Go
и Docker: компиляция, go test и интеграционные запросы здесь НЕ выполнены.
Команды выше запускают эти проверки в вашем рабочем окружении.
